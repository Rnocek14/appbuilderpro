# 04 — The Database (Supabase / Postgres)

**Scope:** `supabase/schema.sql`, `supabase/schema_v2_autopilot.sql`, `supabase/schema_repair.sql`,
`supabase/seed.sql`, `supabase/_apply_garvis_all.sql`, all 125 files in `supabase/migrations/`,
and `docs/automation-triggers-seed.sql`.

This is the master reconstruction of the FableForge + Garvis data layer as of July 2026.
Everything lives in ONE Supabase project (Postgres + Auth + Storage + Realtime + Vault +
pg_cron/pg_net + pgvector). Roughly **124 public tables**, ~35 SQL functions, ~30 triggers,
2 storage buckets, 12 pg_cron jobs, and a single 1536-dim vector space.

---

## 1. How the schema is layered and applied

The database was built in four strata, and the file layout encodes that history:

| Stratum | File(s) | What it is |
|---|---|---|
| 1. Base app-builder schema | `supabase/schema.sql` (v1.0, 357 lines) | The original FableForge Lovable-style app builder: profiles, projects, files, generations, billing, deployments, logs. Non-idempotent (plain `create table`). |
| 2. Autopilot | `supabase/schema_v2_autopilot.sql` | The background build-job queue (`jobs`, `job_milestones`, `agent_questions`, `project_memory`) + the first privilege-escalation fix on the profiles update policy. Applied after schema.sql. |
| 3. Migrations | `supabase/migrations/*` — 9 timestamped `2026*` files + 116 `app_00NN` files (app_0002 … app_0111; **there is no app_0001**) | Everything Garvis. Additive + idempotent by house rule (`create table if not exists`, `drop policy if exists`, enum add via exception blocks). |
| 4. Repair/bundle generators | `supabase/schema_repair.sql` (generated by `scripts/make-schema-repair.py`) and `supabase/_apply_garvis_all.sql` (generated by `scripts/generate-apply-all.mjs`) | `schema_repair.sql` is strata 1+2 rewritten fully idempotent so *any vintage* of the DB can be re-based. `_apply_garvis_all.sql` concatenates every migration **in dependency order**: timestamped 2026* (except `garvis_worker`) → app_00NN → `20260708120000_garvis_worker.sql` **last**, because garvis_worker needs `agent_runs` from app_0003. |

**Important ordering fact:** lexicographic order (what `supabase db push` would use) puts all
`2026*` files before `app_*` files — which would break `garvis_worker` (it references
`agent_runs`, created in `app_0003`). The existence of `_apply_garvis_all.sql` and the recurring
comment "already a member (manual-paste era)" prove the migrations were applied by hand in the
Supabase SQL editor / via the generated bundle, not strictly by CLI timestamp order. The `app_00NN`
prefix is a deliberate manual sequencing convention layered over the Supabase migration folder.

Extensions used: `pgcrypto` (base), `vector` (app_0021), `pg_cron` + `pg_net` (app_0043+),
`btree_gist` (app_0109, for the appointments exclusion constraint), plus Supabase **Vault**
(`vault.secrets`) for the heartbeat URL/secret.

### 4.4 RLS posture
- **Every table has RLS enabled.** The house pattern is `"<table> owner all"` (`owner_id = auth.uid()`
  for ALL, same WITH CHECK) plus, on the earlier tables, `"<table> admin read"` via `is_admin()`.
- **Service-role-only tables** (RLS on, zero client policies): `provider_connections`,
  `oauth_states`, `stripe_events` — and *write-side* service-role-only on `embeddings`,
  `ad_metrics`, `site_events`, `outreach_events`, `social_post_metrics`, `missed_call_events`,
  `system_heartbeat`, `execution_runs` (with the one narrow decision-record carve-out).
- **Anon-insert surfaces** (public web forms): `publish_requests`, `preview_events`.
- **The Wave A lesson (app_0041):** the original `preview_sites` public read `using (true)` leaked
  every tenant's pipeline; it was replaced by a single SECURITY DEFINER RPC returning one
  sanitized row per slug — sanitized further twice (0091, 0103) as new sensitive columns accreted.
- **World-ownership pinning:** from app_0059 onward, WITH CHECK clauses verify that any
  `world_id`/`territory_id` a row points at belongs to the caller (FKs bypass RLS — stated
  explicitly in app_0068). Tables using the pin: standing_orders, draft_verdicts, inbound_mail,

  mls_listings, transaction_timelines, social_posts, reel_jobs, content_weeks, world_rooms,
  world_social_profiles, world_sender_identities.
- **Privileged-column pinning on profiles:** the "update own profile" policy WITH CHECK forces
  role/plan/limit/credits to their current values (recreated in schema.sql → app_0017 → app_0056;

- **Function hardening arc:** credits RPCs granted broadly in 0017, then caller-pinned in 0094

## 5. The vector / embedding architecture

One deliberate, centralized design (app_0021, explicitly learning from "theory-thread's dimension
sprawl — 384/768/1536, mostly unpopulated"):

- **One table, one dimension:** `public.embeddings` with a single `vector(1536)` column,
  default model `text-embedding-3-small`.
- **Polymorphic subjects, no FK:** `(subject_type, subject_id, chunk_ix)` where subject_type ∈
  document | artifact | cluster | knowledge | business | app. Uniqueness per
  (owner, subject_type, subject_id, chunk_ix) makes the embed-worker's writes upserts.
- **Index:** HNSW with `vector_cosine_ops`.
- **Write path:** service-role only (the embed worker holds the provider key); owners get
  read-only RLS. Vectors are never written from the browser.
- **Query path:** `match_embeddings(_owner, _query, _k, _subject_type, _min_similarity,
  _exclude_subject)` — SECURITY INVOKER so RLS applies, plus an explicit owner filter
  (belt-and-suspenders), k capped at 50.
- **Integrity:** because the polymorphic pointer has no FK, app_0054 added AFTER DELETE cleanup
  triggers on documents / knowledge_artifacts / knowledge_clusters / business_profiles plus a
  one-time orphan sweep.
- **Downstream:** `insights` rows ("Garvis noticed…") are produced from vector proximity — the
  score column is documented as "never invented — from cosine."
- Text search is deliberately separate: `garvis_search()` uses ILIKE ("honest at personal scale"),
  with a note that trigram/tsvector could layer on later. The base schema also has a GIN
  tsvector index on project names.

   (anchor last_visit_at, offset 180, window 21) so exactly two fires are due at seed time.
   Requires hand-editing the owner uuid. Dates are relative to `now()`.
3. **In-migration backfills (data-touching migrations):** app_0017 (set every profile's
   credits to the plan grant), app_0054 (orphan embedding sweep), app_0061 (backfill
   `inbound_alias`), app_0082_contacts_world (assign all pre-existing contacts to the owner's
   FIRST world — assumption stated in the file).
4. **`supabase/seed.sql` is NOT platform seed data** — it seeds "LearnFlow" courses / modules /
   lessons / quizzes / quiz_questions, tables that exist nowhere in the platform schema. It is a
   leftover seed for a *generated app* and would fail against the platform DB (see §8).

## 7. Schema evolution, renames, deprecations

- **Naming-convention shift:** timestamped `2026*` migrations (early July 2026) → the
  `app_00NN` manual-sequence convention (0002…0111, no 0001). The generated
  `_apply_garvis_all.sql` exists precisely because lexicographic order is wrong for
  `garvis_worker`.
- **Parallel branches and duplicate numbers:** 0081, 0082, 0086, 0087, 0088, 0091 each exist
  twice with different features. This caused two real production regressions, documented and
  repaired in **app_0092**: (B1) app_0089 recreated the standing_orders kind check without
  `content_week`; (B2) app_0088_consolidation_tick redefined the heartbeat without
  `garvis-social-sync` and never updated disarm. app_0092 is the union + the dual-secret-header
  hardening; app_0096 is the final 12-job form.
- **Billing generations:** `subscriptions` (schema.sql, plan_tier enum, Stripe-ready) was
  superseded by `stripe_subscriptions` (20260702120001) but never dropped — and
  `src/pages/Billing.tsx` still selects from the old table. `plan_tier` remains free/pro only;
  app_0017's comment plans a `'starter'` tier "when wiring Stripe."
- **Deploy generations:** `deployments` (v1 log) → `deploy_bundles` + `projects.netlify_site_id`
  (approval-spine deploys) → `preview_sites.*` hosting columns (demo publishing). All three
  survive.
- **Two "opportunities" tables:** `garvis_opportunities` (app_0012, internal portfolio synergies)
  and `opportunities` (app_0089, external RFPs/grants/jobs). Same word, different features, both
  live — a naming collision to know about.
- **Two customer substrates:** `contacts` (outreach/CRM audience) vs `customers`/`customer_lists`
  (client-owned warm lists for the trigger engine). Deliberate, but easy to confuse.
- **preview_sites accretion:** spec/pitch → strategy/critique/audit → status lifecycle →
  screenshot_url → build_log → hosting columns; the public RPC was re-created three times to keep
  stripping newly-sensitive columns.
- **Check-constraint churn as the extension mechanism:** standing_orders.kind widened five times
  (0059→0079→0080→0088→0089(regression)→0092); opportunities.kind (0102); prospects.status
  (0033); project_assets.source (0030); orchestrator_plans.status (0095). Two of these
  (0079, 0080) were shipped as bug fixes because the UI wrote kinds the DB had never learned —
  inserts failed 100% until the constraint caught up.
- **Enum growth:** approval_kind +send_batch/+send_for_signature/+content_week; mission_status
  +partial/+cancelled; cluster_kind +6 lab kinds; ku_artifact_kind +simulation.
- **Security ratchet over time:** privilege pinning on profiles (3 recreations),
  preview lockdown (0041/0091/0103), server-only project columns (0057), credits caller-pinning
  (0094), approval payload hashing (0069), world/territory ownership pins (0059/0068+),
  narrow ledger insert (0031). Many are framed as fixes from named internal audits
  ("Wave A", "deep scan", "readiness audit", "July 2026 full-system scan", "holy grail gaps").

## 8. Defined-but-unconsumed / planned-but-unused structures

Verified by grepping `src/` and `supabase/functions/` for each table name:

1. **`reel_clips` — zero code references.** The Reel Factory migration (app_0071) modeled
   per-scene text-to-video jobs (sora/runway/luma providers, seeds, statuses) but no client or
   edge function reads or writes the table. `reel_jobs` has exactly one consumer
   (`src/lib/garvis/workingRun.ts`). The per-scene clip engine is schema-only.
2. **`reel_jobs.account_id`** — commented "which faceless account this reel is for (roster lands
   in a later slice)"; no FK, and the account-roster table never arrived.
3. **`supabase/seed.sql`** — seeds LearnFlow tables (`courses`, `modules`, `lessons`, `quizzes`,
   `quiz_questions`) that have **no DDL anywhere in the platform schema**; the only "courses"
   hit in code is a keyword in `src/lib/garvis/verticals.verify.ts`. Orphaned artifact of a
   generated app.
4. **`subscriptions` (legacy)** — superseded by `stripe_subscriptions`; still read by exactly one
   page (`src/pages/Billing.tsx`), so it lingers half-alive.
5. **`knowledge_worlds.mind`** — added in app_0018 explicitly as "written by a later phase;
   schema-ready now."
6. **`app_metrics`** — kept, but app_0008 admits it "is only ever populated by hand, so in
   practice it's empty"; app_liveness was created *because* of that.
7. **`trigger_fires.approval_id`** — "the approval enqueued for this fire (null until wired)" at
   creation (app_0076); the runner wiring came later via the automation seed/runner path.
8. **`client_subscriptions.twilio_subaccount_sid`** — stored "for per-client send routing later."
9. **`customer_lists.business_profile_id`** — a bare uuid with no FK (unlike nearly every other
   link column in the system).
10. **`platform_settings`** admin-model settings and `garvis_constraints` are thinly consumed
    (2 references each) — present, but near the "declared aspiration" end of the spectrum.
11. **The commented-out cron blocks** in `schema_v2_autopilot.sql` (`fableforge-job-tick`) and
    `20260708120000_garvis_worker.sql` were the pre-heartbeat manual recipes; both superseded by
    `garvis_arm_heartbeat()` and kept only as history.
